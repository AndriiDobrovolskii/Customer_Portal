# Spec Review: Refresh Token

**Original Story:** docs/stories/US-2.3-refresh-token.md
**Spec Reviewed:** docs/specifications/US-007-refresh-token-spec.md (2026-09-01 revision, incorporating resolved Open Decisions OD-1–OD-6 and the two carried-forward findings from the 2026-08-22 review)
**Story ID:** US-2.3 (source) / US-007 (spec)
**Reviewed:** 2026-09-01
**Overall Verdict:** Pass with Issues

## Summary

This is a re-review of the 2026-08-22 spec, revised 2026-09-01 to incorporate `docs/decisions/US-2.3-open-decisions.md`'s six resolved Open Decisions, found while clarifying this story against the now-implemented US-2.1/US-2.2 codebase. All six ACs (RT-AC1–RT-AC6) remain covered, and both blocking items from the prior review (RFC 7807 envelope conformance, cookie `Path=/v1/auth` scoping) are now stated explicitly. Verdict remains Pass with Issues: the revision narrows RT-AC2's literal "whole session chain is destroyed" to refresh tokens only (a disclosed, OD-6-sourced substitution, not a silent one), introduces one new check-ordering ambiguity (where the OD-1 rate limit sits relative to the other checks), and two new [Low] missing-edge-case questions (email-delivery failure; a token that is simultaneously expired and reused) — none of which blocks implementation, but all worth resolving before build.

## Ambiguities & Non-Verifiable Statements

- **[Low-Medium] Rate-limit check's position in the check order is unstated.** The spec's Open Decision Resolutions section and FR-2/FR-3/FR-4/FR-6/FR-7 together establish a five-step check order (exists/not-expired → reuse → eligibility → idle timeout → atomic consume, per resolved OD-5), but the NFR introducing the 60/family/hour rate limit ("Refresh requests are rate-limited to 60/family/hour...", Non-Functional Requirements) never states where this check fits relative to the other five. Is it checked first (before even a hash lookup, to bound the cost of a flood of unknown-token requests), or only once a token has been resolved to a real family? A developer implementing the five-step order literally as written would have no place to insert it.

## Contradictions With Original Story

None found as spec-authored conflicts. One place where the revised spec states something narrower than the story's literal text is a disclosed, sourced substitution from the Open Decision Resolutions section, not a silent departure:

- FR-2 narrows RT-AC2's "every token in that family is revoked immediately (**the whole session chain is destroyed**)" to refresh tokens only — "a currently-valid access token tied to this family is not separately revoked and remains usable for its remaining ≤15-minute lifetime" — per resolved OD-6, because `RefreshToken` and `UserSession` have no link to each other in the current schema and this story doesn't add one. This is a real narrowing of the story's own parenthetical claim: `business-glossary.md`'s "Session" entry defines a session as "backed by an access token... and a refresh token... correspond[ing] to one refresh-token family," so "the whole session chain" plausibly meant to include the access token too, not just its refresh-token siblings. The substitution is disclosed and reasoned (OD-6), not hidden, which mirrors how US-2.2's own OD-driven substitutions (e.g. `user_sessions.revoked_at` replacing the story's literal Valkey denylist) were treated in `docs/reviews/specifications/US-006-spec-review.md` — a sourced, disclosed departure, not a spec-authored contradiction.

## Scope Creep

- **[Low] OD-driven content is anchored to the decision log, not to a numbered AC's literal wording.** The Open Decision Resolutions section, the `severity` column and check-order statements throughout FR-2/FR-3/FR-4/FR-6/FR-7, the rate-limit NFR, and the mobile-delivery/access-token-link exclusions in Out of Scope all trace to `docs/decisions/US-2.3-open-decisions.md`, not to RT-AC1–RT-AC6's own text (rate limit and mobile delivery do trace to the story's Assumptions & Defaults table and API Contract line respectively, but their *resolution* — 429+Retry-After, and descoping — is OD-sourced). Same pattern as, and non-blocking for the same reason as, US-2.2's own review finding: every addition narrows, orders, or substitutes existing AC-covered behavior rather than inventing new behavior, but a reader checking spec-against-AC alone, without the decision log, could not derive it.

## Missing Edge Cases, Boundary Conditions & Error Handling

- **[Low] Security-notification email delivery failure is not addressed.** FR-2 requires "a security notification email is sent to the account owner" and now also flags that this needs a new `EmailSender` method, but doesn't state whether the `401`/family-revocation/audit-write outcome is contingent on the email actually sending. The registration flow's own precedent (`app/modules/users/service.py`, "must succeed regardless of whether the verification email goes out") suggests fire-and-forget is this codebase's established pattern, but RT-AC2 doesn't say so explicitly, and this is the first *security alert* (as opposed to a workflow-continuation) email in the codebase, which could reasonably warrant different failure handling.
- **[Low] A token that is simultaneously expired and already-consumed is resolved by FR-3, not FR-2.** Per the check order (exists/not-expired first, reuse second), a replayed token whose `expires_at` has also passed (e.g. a reuse attempt near the 30-day absolute-cap boundary) is rejected by FR-3 as merely "expired" rather than by FR-2 as "reuse" — meaning no family revocation, no `severity=high` audit entry, and no security email fire for that specific replay, even though it's the same reuse-of-a-consumed-token evidence RT-AC2 exists to catch. Does the story intend reuse evidence to still trigger the alerting path once a token is also expired, or is silent rejection acceptable once the family's absolute lifetime has passed anyway (the family is dead either way, so an alert may be less actionable)? Phrased as a question since neither the story nor `business-rules.md`'s BR-008 states an ordering preference here.

## Verdict Rationale

Pass with Issues: full AC coverage (6/6 Covered) and no contradictions in the blocking sense — the one OD-driven substitution (FR-2's access-token carve-out) is disclosed and sourced, consistent with how the analogous US-2.2 revision was reviewed. One [Low-Medium] ambiguity (rate-limit check ordering) and two [Low] missing-edge-case questions (email-delivery failure; expired-and-reused token precedence) remain, plus the standing [Low] OD-anchored scope-creep note — none blocks implementation, but the rate-limit ordering question should be resolved before `db-designer`/`planner` pick an implementation shape for it.

## Addendum — all 3 findings resolved, 2026-09-01

User accepted the recommended resolution for all three: (1) the rate-limit check runs immediately after the token resolves to a `family_id` (right after the hash lookup), before the expiry/reuse/eligibility/idle-timeout/atomic-consume checks; (2) the security-notification email is fire-and-forget, matching the registration verification-email precedent; (3) a token that is both expired and already-consumed is rejected via FR-3 (expired), not FR-2 (reuse) — accepted, since the family is already unusable via the absolute cap regardless. `docs/specifications/US-007-refresh-token-spec.md`'s Non-Functional Requirements section was amended accordingly. Verdict remains Pass with Issues; the only open item is the [Low] OD-anchored scope-creep note, which does not block implementation.
