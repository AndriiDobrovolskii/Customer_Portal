# Spec Review: Support Tickets (Create)

**Original Story:** docs/stories/US-4.1-create-ticket.md
**Spec Reviewed:** docs/specifications/US-4.1-spec.md
**Story ID:** US-4.1 (source story numbered US-4.1)
**Reviewed:** 2026-08-22
**Overall Verdict:** Pass with Issues

## Summary

All seven Acceptance Criteria in the source story (ST-AC1–ST-AC7) are covered by the spec's Functional Requirements (FR-1 through FR-10), with no contradictions found between the two documents. The spec is notably disciplined about not inventing answers where the story is silent — it correctly pushes several genuine gaps (missing-header behavior, idempotency comparison scope, agent queue permissions) into its own Open Questions section rather than guessing. The issues found are two omissions: a security-relevant property of `ticket_number` from the story's Assumptions table isn't carried into the spec's requirements, and the GET endpoint's query parameters (`status`, `cursor`, `limit`), named in the story's API Contract table, are never addressed by any Functional Requirement.

## Ambiguities & Non-Verifiable Statements

- **[Low] Undefined "category" enum** — Spec says: "when `POST /v1/support/tickets` is called with `{subject, body, category}`... an unknown category... the system responds `422`" (FR-3). Neither the spec nor the source story defines the set of valid `category` values, so a developer or QA engineer cannot write a concrete test for "unknown category" without an enumerated list. This ambiguity originates in the story itself (ST-AC3 also just says "unknown category") rather than being introduced by the spec, so it is noted at low severity — but the spec had the opportunity to flag it as an Open Question (as it did for other story gaps) and did not.

- **[Low] "sanitised Markdown" left undefined** — Spec says: "Ticket bodies must be rendered as plain text or sanitised Markdown" (Non-Functional Requirements). What sanitisation rules apply (allowed tags/attributes, library, escaping strategy) is not specified, so this cannot be tested as written. This is carried over verbatim from the story's own Non-Functional / Security Requirements section, so it is not a fidelity defect in the spec, but it remains a build-blocking ambiguity that survived the transformation into requirements.

## Missing Edge Cases, Boundary Conditions & Error Handling

- **[Medium] `ticket_number` "non-guessable" property not captured as a requirement** — The story's Assumptions & Defaults table states: "`ticket_number` (e.g. `CP-2026-0000431`), sequential but non-guessable as an API identifier | Human-readable reference without enabling enumeration." This is an explicit, deliberate security decision in the story (parallel to the attachment-id anti-enumeration requirement, which the spec *does* carry into its Non-Functional Requirements: "Attachment ids must be UUIDv4, never sequential"). FR-1 only says the response includes "a human-readable `ticket_number`" and neither FR-1 nor the spec's Non-Functional Requirements section states that `ticket_number` must resist enumeration/guessing. Without this, an implementation using a simple sequential ID would satisfy the spec as written while violating the story's stated security intent.

- **[Medium] GET endpoint query parameters (`status`, `cursor`, `limit`) unaddressed** — The story's API Contract table lists `GET /v1/support/tickets` with `Request Body: — (query: status, cursor, limit)` and `Success: 200, cursor-paginated`. FR-2 (derived from ST-AC2) describes only the top-level response behavior ("only that customer's tickets, newest first") and never mentions the `status` filter, cursor-based pagination, the `limit` parameter, or how invalid/out-of-range values for any of them should be handled. Since ST-AC2 itself does not test these parameters either, it is unclear whether this is a genuine story gap (in which case the spec faithfully reflects it and no fix is owed here) or content the spec should have surfaced as an Open Question the way it did for the agent-visibility and idempotency-header gaps. Recommend confirming: should pagination/filtering behavior for `GET /v1/support/tickets` be specified before implementation, given it is named in the story's own API Contract?

## Verdict Rationale

Pass with Issues: every Acceptance Criterion is Covered and no Contradictions were found, so the spec is not blocked from a coverage or accuracy standpoint. However, two Medium-severity omissions — the missing non-guessable `ticket_number` requirement and the unaddressed GET query parameters, both traceable to explicit content in the story (the Assumptions table and the API Contract table, respectively) — should be resolved or explicitly deferred via Open Questions before implementation begins, consistent with how the spec already handled its other identified gaps.
