# Spec Review: Password Reset

**Original Story:** docs/stories/US-2.4-password-reset.md
**Spec Reviewed:** docs/specifications/US-008-password-reset-spec.md
**Story ID:** US-2.4 (backlog) / US-008 (spec)
**Reviewed:** 2026-09-01
**Overall Verdict:** Pass with Issues

## Summary

The 2026-09-01 revision (incorporating OD-1–OD-3, the two precedent-resolved items, and the three findings carried forward from the 2026-08-22 review) fully covers all six Acceptance Criteria with no contradictions. The verdict is "Pass with Issues" because three of the Open-Decision-derived clauses (request-side audit logging, the breach-check mechanism's exact form, the rate-limit check order) are transparently disclosed elaborations that go slightly beyond the story's literal AC text — the same OD-anchored scope-creep class this project's own prior spec reviews (US-005, US-006) have flagged and accepted as non-blocking — plus one genuine gap the story itself never addresses: concurrent `confirm` requests against the same token.

## Scope Creep

- **[Low] Request-endpoint audit logging traces to OD-3, not to PR-AC1/PR-AC3's literal text** — Spec FR-1 says: "An `auth_audit_log` entry is written (`event=password_reset_requested`)." Spec FR-3 says the same write "still occurs for this case." Story's PR-AC1 and PR-AC3 (the request endpoint) say nothing about an audit-log entry — only PR-AC2 (confirm) states "an auth_audit_log entry is written." This requirement derives entirely from OD-3, an Open Decision the user resolved during `us-clarifier` on 2026-09-01, not from the story's own AC text. It is transparently disclosed (the spec's "Open Decision Resolutions" section names OD-3 explicitly, and both FRs cite it), matching the same class of finding this project's own US-2.1/US-2.2 spec reviews already carried and accepted as non-blocking.

- **[Low] Breach-check mechanism narrows the story's stated options** — Spec FR-5/NFR say the check runs "against a local static list/bloom filter (OD-1)." Story's NFR says: "The breached-password check MUST use k-anonymity (a 5-character SHA-1 prefix) or a local bloom filter — never transmit the password or its full hash." The story names exactly two mechanisms (a live k-anonymity API call, or a local bloom filter); a plain local *list* (as opposed to a bloom filter specifically) is not literally one of the two. The spec hedges with "or a bloom filter built from one," but leads with the plain-list framing. This is a disclosed, user-approved Open Decision (OD-1), not an invented requirement — flagged for visibility since the literal story text sanctions only the bloom-filter form of "local," not a raw list.

- **[Low] Rate-limit check order and single-Retry-After rule not stated by the story** — Spec FR-6 says checks run "cooldown, then per-account/hour, then per-IP/hour" and the response "uses the `Retry-After` value of the first limit tripped." Story's PR-AC6 states the three limits (60s cooldown, 5/account/hour, 10/IP/hour) but never states an order or a precedence rule for `Retry-After` when more than one is tripped. Derives from OD-2, transparently disclosed and cited.

## Missing Edge Cases, Boundary Conditions & Error Handling

- **[Low] Concurrent `confirm` requests against the same token** — Neither the story nor the spec addresses what happens if `POST /v1/auth/password-reset/confirm` is called twice concurrently with the same valid token (a genuine race, not the already-covered "already consumed" case in PR-AC4, which presumes sequential ordering). The token is explicitly "single-use" (story's Assumptions & Defaults #2, FR-1), and this codebase has an established precedent for exactly this kind of race — US-2.3's refresh-token consumption uses an atomic `UPDATE...WHERE consumed_at IS NULL RETURNING` specifically to guarantee single-use under concurrency (RT-AC6). The story gives no equivalent AC here, so this is raised as a question rather than an assertion: should password-reset confirmation guarantee atomic single-use consumption the same way, or is this scenario considered out of scope for this story?

## Verdict Rationale

Pass with Issues: all six ACs (PR-AC1–PR-AC6) are fully Covered and no contradictions were found, so nothing here blocks implementation outright. The three Scope Creep notes are disclosed, user-approved Open-Decision elaborations rather than invented requirements — the same pattern already accepted in this project's prior spec reviews — and the one Missing Edge Case is a genuine question worth a decision (likely by `planner`/`implementation-planner`, following the US-2.3 precedent) before or during PLANNING rather than a blocker to SPECIFICATION sign-off.
