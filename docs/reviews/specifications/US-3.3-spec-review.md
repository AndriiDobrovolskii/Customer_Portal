## Summary

This is a re-run after `docs/stories/US-3.3-view-audit-information.md` was amended (2026-09-02): AU-AC4's Gherkin now states only the `405` requirement (the DB-grant clause moved to a documented note tracking it as a separate, project-wide follow-up, OD-12), and the Data Model Notes' "monthly" partition line was corrected to "daily," removing the story's own prior self-contradiction. Both changes are exactly what this review's prior two runs identified — nothing beyond them changed. All 9 Acceptance Criteria are now fully Covered on independent comparison against the amended AC text, and no Contradiction remains between the spec and the (now-consistent) story. Several genuine ambiguities and missing edge cases remain — mostly the spec's own carried-forward Open Questions, independently confirmed here — which is why the verdict is Pass with Issues rather than a clean Pass.

## Ambiguities & Non-Verifiable Statements

- **[Medium] Historical-row field availability for AU-AC1 is unresolved** — Spec says: "Whether the view synthesizes these fields for historical rows... or this guarantee only holds for rows written after this story's migrations land is not stated in the source and is not decided here" (FR-1). A developer cannot write a single test for "each entry contains... actor_role... and an outcome" without knowing which of the two behaviors is intended for pre-migration rows.
- **[Medium] Write target for FR-2/FR-3's own audit entries is unresolved** — Spec says: "Which underlying table this write lands in is not decided by this spec... If `audit_log` ends up being a view, this write needs a concrete per-domain target table" (FR-2). This is not a cosmetic gap: `POST`-equivalent behavior (writing `audit_log_viewed`/denial entries) cannot be implemented without knowing where the row goes.
- **[Low] "Fields marked sensitive" is undefined** — Spec says: "Fields marked sensitive are stored redacted" (FR-6), same phrase as the source's AU-AC6. Neither document enumerates the complete list beyond the four named exclusions. Carried forward from the pre-existing 2026-08-22 review, still unresolved.
- **[Medium] Hash-chain concurrency is unaddressed** — Spec says the trigger computes `previous_hash` from "the previous row's hash" (FR-7) but does not state how correctness is preserved under concurrent `INSERT`s into the same daily partition. Carried forward from the pre-existing review; still open despite the daily-partition resolution (OD-11) — the concurrency question is orthogonal to which unit the partition uses.
- **[Low] AU-AC8's "direct identifier" scope for `payload` JSONB is unenumerated** — Spec says "every direct identifier the entries contained (email, display_name, ip)" (FR-8), verbatim from the source, non-exhaustive. Whether identifiers inside the `payload` JSONB column are also in scope is unstated. Carried forward.

## Contradictions With Original Story

None. The prior run's finding (spec said "daily" partitions while the story's own Data Model Notes said "monthly") is resolved — the story's Data Model Notes line was corrected to "daily" (2026-09-02, OD-11), matching both the spec and the story's own Assumption #4/AU-AC7, which always said "daily." No other contradiction was found.

## Scope Creep

No findings. The Open Decision Resolutions section (OD-1/OD-2/OD-11/OD-12) introduces content not literally present in the story — most notably a new, minimal, provisional erasure script (OD-2) and a renamed pre-existing table (OD-1) — but all of it traces to a specific Open Decision `us-clarifier` raised against the real codebase and the user explicitly resolved during CLARIFICATION (`docs/decisions/US-3.3-open-decisions.md`), which is this project's established, precedented mechanism for closing gaps a story leaves open (matching, e.g., US-2.5's spec incorporating its own resolved OD-2's AES-GCM encryption mechanism, not flagged as scope creep by that story's own review). Every other FR/NFR/Out-of-Scope line traces cleanly to a corresponding AC or the source's own Non-Functional/Security Requirements or Out of Scope sections.

## Missing Edge Cases, Boundary Conditions & Error Handling

- **[Resolved this re-run] Identifier redaction across structurally inconsistent free-text fields (AU-AC8/FR-8)** — The prior run's High finding is resolved: FR-8 now specifies field-aware redaction (OD-13) for `profile_audit_log.old_value`/`new_value`, so `display_name` — one of AU-AC8's three named identifiers — is no longer left unaddressed. The narrower question of whether `payload` JSONB can also embed identifiers remains open (see Ambiguities, unchanged from the prior run).
- **[Medium] Hash-chain genesis rule is unstated (AU-AC7/FR-7)** — FR-7 says the chain is "seeded with the previous day's partition's final hash" but does not state what the very first partition seeds from, or what a day seeds from when the prior day's partition has zero rows. AU-AC7's "reports the exact row at which the chain breaks" guarantee is not verifiable without a defined genesis rule. This is a new finding, not present in the pre-existing 2026-08-22 review (it predates the daily-partition resolution this gap depends on).
- **[Low, question] Single missing `from`/`to` bound is unaddressed (AU-AC5)** — Carried forward unchanged from the pre-existing review: AU-AC5 only specifies behavior when the range exceeds 90 days or omits *both* bounds; a single missing bound's behavior (reject, default, open-ended) is unstated in both story and spec.
- **[Low, question] Cold-storage target for AU-AC9 remains unresolved** — Carried forward from the source's own Open Questions section; on the same footing as the account-erasure legal/DPO policy question OD-2 also left open.

## Verdict Rationale

Pass with Issues: full AC coverage (9/9 Covered under independent review) and no contradictions were found, so the verdict does not fail. Six ambiguities and edge-case gaps remain (see above), all but one carried forward unchanged from the pre-existing 2026-08-22 review and none newly introduced by this run — none blocks implementation outright, but they are worth resolving or explicitly deferring during DESIGN, particularly the hash-chain genesis rule (FR-7) and the still-open write-target question for FR-2/FR-3 (does `audit_log` end up a table or a view — db-designer's first decision).
