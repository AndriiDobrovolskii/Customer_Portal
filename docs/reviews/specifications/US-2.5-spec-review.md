# Spec Review: Multi-Factor Authentication (TOTP)

**Original Story:** docs/stories/US-2.5-mfa-totp.md
**Spec Reviewed:** docs/specifications/US-2.5-spec.md
**Story ID:** US-2.5 (source backlog file uses US-2.5)
**Reviewed:** 2026-09-01 (re-run against the 2026-09-01 revision)
**Overall Verdict:** Pass with Issues

## Summary

This re-review covers the 2026-09-01 revision of the US-2.5 spec, which incorporates all 11 Open Decisions from `docs/decisions/US-2.5-open-decisions.md` after US-3.2 (Manage Roles) reached PR and merged. All 7 Acceptance Criteria (MF-AC1–MF-AC7) remain fully covered, and no contradictions with the source story were found. The issues found are: one genuine data-model gap the spec's own OD-7 resolution depends on but never accounts for (no timestamp exists to compute "since the role was granted"), two ambiguities in how the new two-trigger enrolment-scoped-token mechanism interacts with the existing login-challenge and refresh-token flows, and disclosed scope additions (the `mfa_reenrollment_required` flag, the `perm_epoch`/`token-stale` reuse, and FR-8's wholly-new disable-success behavior) that are legitimate, user-approved Open Decision resolutions but still introduce mechanisms the original story never mentions.

## Ambiguities & Non-Verifiable Statements

- **[High] No data source for "the moment the role was granted"** — Spec says (FR-6): "During a 14-day rollout grace period starting from the moment the role was granted..." But `app/modules/roles/models.py`'s `UserRole` table has only `user_id` and `role_id` — no timestamp column. `admin_audit_log` records role changes (`old_roles`/`new_roles`, `occurred_at`) but the spec never states that the grace-period clock reads from that table, nor addresses what happens if a user has been re-granted the same role more than once (which `old_roles`/`new_roles` row would the login-time check use?). A developer cannot implement the 14-day window as written without this being resolved first.
- **[Medium] Grace period scope unclear for the recovery-code trigger** — FR-6 ties the 14-day grace period explicitly to "the moment the role was granted." FR-7 says a consumed recovery code causes "the next successful login... issues the enrolment-scoped token described in FR-6," but never states whether that login also gets a 14-day grace period (and if so, dated from when — the moment of consumption?) or whether the recovery-code trigger scopes the token immediately with no grace period at all. The two triggers are described as sharing the same *mechanism* (FR-6/FR-7 cross-references) but not clearly the same *grace-period policy*.
- **[Low] Precedence between FR-3 (MFA login challenge) and FR-6 (enrolment-scoped token) is implied, not stated** — FR-6's trigger condition is "`mfa_enabled` is `false`," which is mutually exclusive with FR-3's precondition (`mfa_enabled = true`), so the two paths cannot both apply to the same login in practice — but the spec never says so explicitly, leaving a reader to infer it from the two conditions rather than being told directly.

## Scope Creep

- **[Low] `users.mfa_reenrollment_required` and the two-trigger enrolment-scoped-token generalization** — Spec says (FR-2, FR-6, FR-7): a new stored flag and a token-scoping mechanism triggered by either a privileged-role grant *or* recovery-code use. Nothing in the story's Data Model Notes, API Contract, or any AC describes this flag or a second trigger for the enrolment-scoped token — MF-AC7 only says the user is "emailed a security notification and prompted to re-enrol." This is a disclosed, user-approved Open Decision (OD-5, which explicitly overrode the recommended advisory-only default), not a silent invention, but it is genuinely new scope relative to the source story.
- **[Low] `perm_epoch`/`token-stale` reuse as the enrolment-scoped-token exit condition** — Spec says (FR-2, FR-6): activation "sets `perm_epoch:{user_id}`... the next call... responds `401 token-stale`." The source story never mentions `perm_epoch` or a dependency on the `roles` module's exit mechanism — this is a cross-module design decision (OD-7) disclosed in Open Decision Resolutions, not present in the story itself.
- **[Low] FR-8 (`DELETE /v1/auth/mfa` non-privileged success path) has no corresponding AC** — The story's API Contract table documents a `204` response for this call, so the endpoint and status code are not invented, but none of MF-AC1–MF-AC7 narrates its behavior (state changes, purge, audit event, session revocation). FR-8's content is disclosed as resolving OD-6/OD-8, both independently flagged by this same review's prior (2026-08-22) run — legitimate gap-filling, but worth noting FR-8 traces to an Open Decision, not an AC.

## Missing Edge Cases, Boundary Conditions & Error Handling

- **[Medium] Refresh-token behavior while enrolment-scoped is unaddressed** — FR-6/FR-2 describe `perm_epoch` invalidating the *access* token only, leaving the refresh family intact (the same invariant US-3.2 established). If an enrolment-scoped account calls `POST /v1/auth/refresh` before completing enrolment (rather than logging in again), does the newly minted access token come back enrolment-scoped too (since the underlying condition — privileged role, `mfa_enabled = false` — still holds), or does refresh unconditionally restore a full-access token? FR-6's language ("on every successful login... the system resolves the user's role names") is specific to the login endpoint and doesn't say whether `/auth/refresh` re-runs the same check.
- **[Low] Does a role demotion clear an in-progress enrolment-scoped-token requirement?** — If a privileged role is removed from an account that is currently enrolment-scoped (per FR-6) before that account completes enrolment, the spec doesn't explicitly state that the *next* login re-evaluates the condition and would naturally stop scoping the token (a fair inference from "on every successful login," but not stated as a boundary case).

## Verdict Rationale

Pass with Issues: full AC coverage (7/7) and no contradictions were found, so the spec is not blocked outright. However, one High-severity data-model gap (no timestamp backs the 14-day grace-period clock FR-6 depends on) should be resolved before `db-designer`/`planner` proceed, since it affects whether a new column or a different data source (e.g. `admin_audit_log`) is needed. The remaining ambiguities, disclosed scope additions, and edge cases are worth resolving but do not block moving into DESIGN.
