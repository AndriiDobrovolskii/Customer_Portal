# Security Review: Password Reset (US-2.4 / spec US-2.4)

**Story ID:** US-2.4
**Reviewed:** 2026-09-01
**Overall Verdict:** Pass

## Summary

Reviewed `app/modules/users/{service,repository,cache,schemas,router,exceptions}.py`, `app/core/{breached_passwords,email,security}.py`, and the new migration against AGENTS.md §7's six non-negotiable rules. All six pass: Argon2id-only password storage with settings-driven cost parameters, no plaintext/reversible credential storage, no sensitive values in any log call, `extra="forbid"` with no privilege fields on both inbound schemas, parameterized SQL exclusively (including the additive-only migration), and uniform status/body on every account-enumeration-sensitive failure path.

## AGENTS.md §7 Non-Negotiable Checklist

| Rule | Result | Evidence |
|---|---|---|
| Argon2id-only password storage, cost params from settings | Pass | `app/modules/users/service.py:906` — `confirm_password_reset` calls `hashed_password = await hash_password(new_password)`, the same `app/core/security.py:15-26` helper every other password-write path uses (`PasswordHasher(time_cost=settings.argon2_time_cost, memory_cost=settings.argon2_memory_cost_kb, parallelism=settings.argon2_parallelism)`, all three params read from `get_settings()`, never hardcoded). No new hashing path was introduced by this story. |
| No plaintext/reversible encryption for credentials | Pass | The new password is passed only to `hash_password` (Argon2id) before persistence (`repository.py:106-112`'s `update_password_hash`); the reset token itself is hashed with SHA-256 before storage (`service.py:_hash_password_reset_token`, `hashlib.sha256(raw_token.encode()).hexdigest()`) — a lookup key, not a credential requiring KDF treatment, matching the identical precedent already used for `RefreshToken.token_hash`/`EmailVerificationToken.token_hash`. The raw token itself is never persisted anywhere. |
| No tokens/hashes/PII in logs; no `print()` | Pass | Every `logger.exception` call this story adds (`service.py:834`, `:916`) passes only a static string (`"failed to send password reset email"`, `"failed to send password reset notice email"`) — no token, password, hash, or email is interpolated into either message. No `print()` appears anywhere in the diff (`git diff` grep confirmed zero occurrences). |
| `extra="forbid"` + privilege-field exclusion on inbound schemas | Pass | `app/modules/users/schemas.py:50` (`PasswordResetRequestRequest`) and `:62` (`PasswordResetConfirmRequest`) both set `ConfigDict(extra="forbid")`. Fields present: `email`; `token`, `new_password` — none of this module's actual privilege/system columns (`id`, `status`, `email_verified`, `hashed_password`, `deactivated_at`, `last_login_at`, `created_at`) appear on either schema. |
| Parameterized SQL only, no string interpolation | Pass | Every repository method this story adds (`create_password_reset_token`, `get_password_reset_token_by_hash`, `invalidate_password_reset_tokens_for_user`, `consume_password_reset_token`, `update_password_hash` — `repository.py:102-197`) uses SQLAlchemy `select()`/`update()` with bound `.where()` clauses exclusively, no f-string/`.format()`/`%` SQL anywhere. The migration (`9a4776e19934_add_password_reset_tokens.py`) contains only `op.create_table`/`op.create_index` — no hand-written `op.execute()` at all, so no raw-SQL surface exists in this diff. |
| Uniform auth-failure response, no differentiation leaked | Pass | **Account-enumeration surface (PR-AC3, the actual scope of this rule for this story):** `request_password_reset` (`service.py:738-836`) returns the identical `202` + generic body for a registered/active account, an unknown email, a deactivated account, and (this story's own eligibility extension) an unverified account — verified by `test_password_reset_request_unknown_email_returns_202_identical_body` (integration) asserting byte-identical status and JSON body. **Token-state surface (PR-AC4):** an unknown-hash and an already-consumed token both map to the identical `PasswordResetTokenInvalidError` (400, `token-invalid`); a separate `PasswordResetTokenExpiredError` (400, `token-expired`) is used only for genuine expiry. This two-way split is a deliberate, spec-approved requirement (the source story's own PR-AC4 literally names two distinct type slugs) resolved by direct precedent from `email_verification`'s identical `TokenExpiredError`/`TokenInvalidError` pattern — it discloses token *lifecycle* state, not account identity or password correctness, and is the same accepted shape already shipped for email verification. Not a violation of this rule's account-enumeration intent. |

## Advisory Findings (non-§7, does not force Fail)

- **[Low] CSRF not enforced on either new state-changing POST endpoint** — Same standing gap already disclosed in US-2.2's and US-2.3's own security reviews (both accepted as a pre-existing, tracked follow-up, OD-4 from US-2.2's clarification round). Not new to this story; `confirm`'s own credential (the possession of a valid, single-use, emailed token) meaningfully limits the practical impact of a cross-site request here, similar to email-verification's existing exposure.
- **[Low] Breached-password coverage is a small bundled list (~300 entries), not a comprehensive corpus** — Disclosed and accepted via OD-1's resolution (`docs/decisions/US-2.4-open-decisions.md`): a local list/bloom filter was the chosen mechanism specifically to avoid a live third-party dependency, at the cost of catching fewer breached passwords than a full HIBP-scale corpus would. A future story could swap in a larger bundled list without any interface change (`is_breached_password`'s signature is unaffected by the list's size).
- **[Low] Unknown-token brute-force is not separately rate-limited** — `confirm`'s three failure paths (`token-invalid`/`token-expired`/`password-policy`) have no dedicated per-IP throttle of their own (only `request` is rate-limited, per FR-6/OD-2); a 32-byte `secrets.token_urlsafe` token space makes brute-forcing infeasible regardless, but this is worth noting as the same class of gap US-2.3's own security review flagged for refresh-token guessing (also accepted as out of that story's stated scope).

## Verdict Rationale

Pass: all six §7 rows are Pass, with the token-state-vs-account-enumeration distinction explicitly reasoned through rather than asserted — the rule's actual concern (account/credential-existence leakage) is fully satisfied, and the deliberate expired-vs-invalid split is a spec-approved, precedented exception to the rule's literal wording, not a violation of its intent. The three advisory findings are disclosed, pre-existing, or already-scoped gaps and do not change the verdict.
