# Security Review: Multi-Factor Authentication / TOTP (US-2.5 / spec US-2.5)

**Story ID:** US-2.5
**Reviewed:** 2026-09-02
**Overall Verdict:** Pass (1 finding found and fixed same-day)

## Summary

Reviewed `app/modules/users/{models,schemas,repository,service,router,exceptions,dependencies,cache}.py`, the cross-cutting additions to `app/core/{crypto,security,config,email}.py`, and migration `cef55228a927` against AGENTS.md §7's six non-negotiable rules. Recovery codes are Argon2id-hashed like every other credential in this codebase; the TOTP secret itself is the one field in this story that is deliberately *not* hashed, for a reason specific to how TOTP works (rule 2 below). No sensitive value appears in any of this story's log calls. All four new inbound schemas set `extra="forbid"` with no privilege field (already confirmed by `implementation-verifier`, cross-referenced here rather than re-derived). The migration and every new repository method use SQLAlchemy bound-parameter constructs exclusively — this story's migration has no raw `op.execute()` at all, so rule 5 needed no precedent-matching the way US-3.2's did. Rule 6's audit surfaced a real defect in `disable_mfa`: its two-factor check let a stolen bearer session distinguish "wrong password" from "wrong code" via the response body, which — given this endpoint's specific threat model — narrowed a brute-force search. Fixed same-day; see the rule-6 row and Advisory Findings.

## AGENTS.md §7 Non-Negotiable Checklist

| Rule | Result | Evidence |
|---|---|---|
| Argon2id-only password storage, cost params from settings | Pass | Recovery codes are the one new credential-like value this story introduces, and they go through the exact same `hash_password`/`verify_password` pair (Argon2id, cost params sourced from `get_settings()` inside `app/core/security.py`, unchanged by this story) every other credential in this codebase uses: `app/modules/users/service.py:1168` (`activate_mfa`, `hash_password(code)` when generating the 10 recovery codes) and the recovery-code candidate loop inside `verify_mfa`/`_try_consume_recovery_code` (`verify_password(candidate, stored.code_hash)`). No new hashing scheme, no hardcoded cost parameter. |
| No plaintext/reversible encryption for credentials | Pass, reasoned explicitly | `User.mfa_secret_encrypted` (`app/modules/users/models.py`) is stored via AES-GCM envelope encryption (`app/core/crypto.py`'s `encrypt_mfa_secret`/`decrypt_mfa_secret`), which is reversible by design — but the TOTP secret is not a "credential" in the password/recovery-code sense this rule targets. A TOTP secret must be *recomputed from* to verify a submitted code (`verify_totp_code` in `app/core/security.py` derives the expected 6-digit code from the decrypted secret and compares); there is no one-way hash that could serve this purpose, since hashing would make verification impossible. This is the industry-standard shape for TOTP secret storage specifically because of that constraint — it is not a substitute for Argon2id sneaked in where a one-way hash was possible, which is what this rule forbids. Contrast recovery codes above: those *can* be one-way hashed (verification is compare-only, never recompute), and correctly are. |
| No tokens/hashes/PII in logs; no `print()` | Pass | Every `logger.exception` call this story touches or adds passes only a static string, none of them anywhere near a secret value: `app/modules/users/service.py:1289` (`"failed to send mfa recovery-used notice email"`), plus the pre-existing calls at `:665`/`:674`/`:936`/`:1034`/`:1116` (unrelated to this story but re-confirmed unaffected). Grepped `app/modules/users/service.py`, `app/core/{crypto,security}.py` for `logger\.`/`print(` — no call anywhere interpolates a TOTP secret, recovery code, `mfa_token`, or `MfaEnrollResponse.secret`; `grep -n "\.secret\b" app/modules/users/service.py` → zero matches (the value is returned in the response schema, never logged). No `print()` in any touched file. |
| `extra="forbid"` + privilege-field exclusion on inbound schemas | Pass | Cross-referenced from `implementation-verifier`'s already-cited finding (`docs/verification/US-2.5-implementation-verification.md` §6.7): `app/modules/users/schemas.py` — `MfaEnrollRequest` (`current_password` only), `MfaActivateRequest` (`code` only), `MfaVerifyRequest` (`mfa_token`, `code`), `MfaDisableRequest` (`current_password`, `code`) all set `ConfigDict(extra="forbid")`. None exposes `id`, `mfa_enabled`, `mfa_activated_at`, `mfa_reenrollment_required`, or any other privilege/system column this story added to `User`. |
| Parameterized SQL only, no string interpolation | Pass | `app/modules/users/repository.py`'s 8 new methods (`update_mfa_pending_secret`, `activate_mfa`, `set_mfa_reenrollment_required`, `disable_mfa`, `create_recovery_codes`, `list_unconsumed_recovery_codes`, `consume_recovery_code`, `delete_recovery_codes_for_user`) use `update()`/`select()`/`delete()` with bound `.where()` clauses exclusively — no f-string/`.format()`/`%` SQL anywhere. Unlike US-3.2's review, this rule needed no precedent-matching: migration `cef55228a927` contains zero `op.execute()` calls of any kind — every statement is `op.create_table`/`op.create_index`/`op.add_column`/their `drop_` inverses, all parameter-free DDL by construction (confirmed by reading the migration file in full). |
| Uniform auth-failure response, no differentiation leaked | Pass (after same-day fix) | **Found:** `disable_mfa`'s original implementation checked `verify_password` first (raising `InvalidCredentialsError`, 401, on failure) and only then checked the TOTP code (raising a *different* exception, `MfaInvalidCodeError`, also 401, on failure). Because the code check was only reached after the password check passed, receiving `mfa-invalid-code` in the response body already confirmed the password was correct — a caller holding a stolen bearer token (this endpoint's actual threat model: the spec's own NFR is that a hijacked session must not be able to strip the second factor) could use the distinct `type` slug as an oracle to brute-force the password and the code independently rather than needing both simultaneously, halving the effective search space. **Fixed:** `app/modules/users/service.py:1334` (`disable_mfa`) now evaluates `password_ok` and `code_ok` unconditionally (never short-circuited, so no timing signal either) and raises the single `InvalidCredentialsError` on either failure — the response is byte-identical regardless of which factor was wrong. The privileged-role check (`409`) still runs only after both factors succeed, so a wrong password/code never reveals whether the account is privileged either. Regression-guarded by `test_disable_mfa_wrong_password_and_wrong_code_are_indistinguishable` (`tests/unit/modules/users/test_users_service.py`), which asserts both failure paths raise the identical exception type and args. `verify_mfa`'s own uniform-401 behavior (wrong TOTP vs. wrong recovery code vs. invalid/expired `mfa_token` — all `MfaInvalidCodeError`) was unaffected and re-confirmed correct; it never had this issue because it has only one factor to check, not two. |

## Advisory Findings (non-§7, does not force Fail)

- **[Low] `disable_mfa`'s `user is None` branch is a separate, currently-untested statement.** The rule-6 fix restructured the method to `if user is None: raise InvalidCredentialsError` before computing `password_ok`/`code_ok` (needed to avoid an `assert` — banned by this project's ruff `S101` rule — for mypy's narrowing). This branch is reachable only if a valid, already-authenticated bearer token resolves to a `user_id` with no matching row (the account was deleted mid-session) — not a caller-controlled path and not part of any AC, so no test currently exercises it directly, matching this same file's existing untested equivalents in `activate_mfa`/`enroll_mfa`'s own `user is None` folds. Not a security gap: the response is the same generic 401 either way.
- **[Low] Recovery-code and TOTP verification share one exception type by design (`MfaInvalidCodeError`), confirmed correct.** `verify_mfa` folds "wrong TOTP," "wrong/already-consumed recovery code," and "no matching `mfa_token`" all into the same 401 — this was already a deliberate design choice (FR-7/API design) rather than something this review changed, and it correctly extends the same anti-oracle reasoning the rule-6 fix applies to `disable_mfa`.
- **[Low] `MfaEnrollResponse.secret`/`MfaActivateResponse.recovery_codes` are one-time plaintext disclosures, already reasoned through by `implementation-verifier`.** Re-confirmed here from a logging angle specifically: neither value is logged anywhere, and neither is returned again by any other endpoint after the initial response.

## Verdict Rationale

Pass: five of the six rules were clean on first read with cited evidence, including one (rule 2) that required explicit reasoning through an apparent tension — AES-GCM envelope encryption for the TOTP secret is correct, not a violation, because the secret must be recomputed-from rather than compared-against, unlike a password or recovery code (both of which correctly use Argon2id here). Rule 6 surfaced a genuine defect: `disable_mfa`'s sequential two-factor check let a stolen bearer session narrow a brute-force search via the response body. This was fixed same-day (joint, unconditional evaluation of both factors collapsing to one exception type), verified with a dedicated indistinguishability test, and the full gate re-run green (`pre-commit run --all-files` 7/7, `mypy app tests` clean, 361/361 tests, 97.35% coverage). Per this skill's own rule, a genuine same-day fix is reported as Pass with the finding documented as found-and-fixed, not as a Fail — the story is not being handed back with an open defect.
