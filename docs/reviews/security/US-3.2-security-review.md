# Security Review: Manage Roles (US-3.2 / spec US-3.2)

**Story ID:** US-3.2
**Reviewed:** 2026-09-01
**Overall Verdict:** Pass

## Summary

Reviewed `app/modules/roles/{models,schemas,repository,service,router,dependencies,exceptions}.py`, the cross-cutting changes to `app/core/{security,revocation_cache,cache_keys,config}.py` and `app/modules/users/{service,exceptions,dependencies}.py`, and both new migrations against AGENTS.md §7's six non-negotiable rules. This story introduces no new credential storage (rules 1–2 are N/A, confirmed no such field exists anywhere in the diff), no sensitive values in the one new log call, `extra="forbid"` with no privilege fields on the one inbound schema, parameterized SQL everywhere except the migration's seed-data `INSERT`s (which match this project's own established precedent for static, author-written migration SQL), and no new account/credential-enumeration surface.

## Advisory Findings (non-§7, does not force Fail)

- **[Low] `PermissionEpochCache.get_perm_epoch` degrades open, unlike `revoke_before`'s fail-closed denylist semantics** — `app/modules/users/service.py:517-524` wraps the `perm_epoch` read in the identical fail-closed `try`/`except Exception: return None` (reject the token) pattern as `revoke_before` — confirmed this is *not* actually a gap, both checks fail closed identically. Noted here only because a careless future reader might assume `perm_epoch` (a UX-smoothing mechanism, not a security denylist per se) could reasonably degrade open on a cache outage; it deliberately doesn't, and that choice is correct (an unreachable cache should never silently accept a token that might be stale).
- **[Low] `require_scope`'s dependency ordering** — `app/modules/roles/router.py` puts `Depends(require_scope(...))` in the route decorator's `dependencies=[...]` list, which FastAPI resolves before the handler's own parameters (including `CurrentUserDep` when the handler also depends on it directly, as `replace_user_roles` does). Both resolve to the same cached `get_current_user` call within one request (FastAPI's dependency cache), so there's no double-authentication cost and no ordering bug — noted only as a pattern worth being consistent about if more `/v1/admin/*` routes are added later.
- **[Low] Seed-data UUIDs are fixed literals, not app-generated** — `e50fbe8161fc`'s seed `INSERT`s use hardcoded UUID literals (`11111111-...`, `a1111111-...`, etc.) for the four roles and six permissions, rather than `uuid.uuid4()`-style random values. This is intentional and correct for a reproducible, idempotent seed migration (a random UUID regenerated on every fresh `alembic upgrade head` run would break the `ON CONFLICT (name)`/`ON CONFLICT (scope)` idempotency this story relies on), not a security concern — noted only so a future reader doesn't mistake the low-entropy pattern for an oversight.

## Verdict Rationale

Pass: two of the six rules are correctly N/A (no credential material in this story's scope), the remaining four are Pass with cited evidence, and the one rule requiring genuine reasoning (parameterized SQL vs. the migration's raw `op.execute()` seed data) is resolved by direct, already-established precedent in this exact codebase rather than asserted. The uniform-response rule's apparent tension with this story's several distinct 403/409/422 codes is explicitly reasoned through: those are authorization-outcome differentiation for an authenticated actor, not the account-enumeration leak §7 protects against. Three Low advisory findings are noted for completeness; none force a Fail.
