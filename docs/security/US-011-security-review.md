# Security Review: Manage Users (US-3.1 / spec US-011)

**Story ID:** US-011
**Reviewed:** 2026-09-02
**Overall Verdict:** Pass

## Summary

Reviewed `app/modules/admin_users/` and its cross-cutting changes to `roles`/`account`/`users` against `AGENTS.md` §7's six non-negotiable rules. All six check out clean. This story introduces no new password/credential handling at all (creation is invitation-only, and `POST /v1/admin/users` structurally cannot accept a `password` field), which makes rows 1-2 and 6 straightforward rather than requiring new reasoning — the one placeholder credential value this story writes (`hashed_password=""` for a newly invited user) was checked explicitly and confirmed safe by construction, not just assumed.

## AGENTS.md §7 Non-Negotiable Checklist

| Rule | Result | Evidence |
|---|---|---|
| Argon2id-only password storage, cost params from settings | Pass (N/A — no password handling) | `app/modules/admin_users/service.py`/`repository.py` never call `hash_password`/`verify_password`. `CreateUserRequest` (`schemas.py`) has no `password` field, so a submitted one is rejected by `extra="forbid"` before the service runs (FR-7) — this story cannot write a real password hash at all. `repository.py`'s `create()` (line ~135) sets `hashed_password=""` for the new `invited`-status row, a placeholder, not a credential — Argon2id's own hash format (`$argon2id$v=19$...`) can never be the empty string, so no password attempt can successfully verify against it; the account is authentication-inert until a separate (out-of-this-story's-scope) invitation-completion flow writes a real hash. |
| No plaintext/reversible encryption for credentials | Pass (N/A) | Same reasoning as above — no credential of any kind is stored, encrypted, or transmitted by this story. `InvitationToken.token_hash` (`admin_users/models.py`) is a SHA-256 digest of a random `secrets.token_urlsafe(32)` value, matching the existing `EmailVerificationToken`/`PasswordResetToken` precedent exactly — a one-way hash of a bearer token, not a credential-encryption case this rule targets. |
| No tokens/hashes/PII in logs; no `print()` | Pass | `admin_users/service.py`'s only logging call (line 256): `logger.exception("failed to issue invitation token after admin user creation")` — a static string, no interpolated email, token, or hash. Grep confirms zero `print()` calls anywhere in `app/modules/admin_users/`. |
| `extra="forbid"` + privilege-field exclusion on inbound schemas | Pass | `admin_users/schemas.py`: `CreateUserRequest`, `UpdateUserRequest`, `DeactivateUserRequest` all set `model_config = ConfigDict(extra="forbid")`. Cross-checked against `User`'s real column set (`app/modules/users/models.py`): none of the three declares `id`, `created_at`, `email_verified`, `status`, `deactivated_at`, `hashed_password`, `last_login_at`, or any `mfa_*` column. `UpdateUserRequest` additionally excludes `email` and `roles` by omission — checked against the raw request body pre-validation in `update_user()` (service.py) so a submission naming them is rejected before this schema even runs. |
| Parameterized SQL only, no string interpolation | Pass | `admin_users/repository.py`: every query uses `select()`/`update()`/SQLAlchemy ORM construction — grep confirms zero f-string/`.format()`/`%`-interpolated SQL. The two migrations' only hand-written `op.execute()` calls (`1b2b1d52dd71` lines 42, 81: `"CREATE EXTENSION IF NOT EXISTS pg_trgm"` / `"DROP EXTENSION IF EXISTS pg_trgm"`) are fixed, static strings with no variable interpolation of any kind — no injection surface exists in either. |
| Uniform auth-failure response, no differentiation leaked | Pass (N/A — no new authentication path) | This story introduces no new *authentication* check — every `401` on every `admin_users` route is produced by the existing, previously-audited `CurrentUserDep`/`get_authenticated_user` choke point (unchanged by this story). `admin_users`'s own new checks (403 insufficient-permission, 404 not-found, 409 conflicts) are *authorization*/business-state checks, not password/credential verification, so this rule's specific concern (e.g. distinguishing "wrong password" from "unknown account") doesn't have a direct analogue here. The one place this story's own logic *could* have introduced an enumeration-style leak — `GET /v1/admin/users/{id}` and `PATCH .../{id}` both return a uniform `404 not-found` for an unknown id regardless of whether the id was ever valid, never a distinguishing signal. |

## Advisory Findings (non-§7, does not force Fail)

- **[Low] Invitation-completion flow (setting a real password) is out of this story's stated scope but not yet built anywhere in this codebase.** `POST /v1/admin/users` creates a `status="invited"` account with `hashed_password=""` and emails an invitation token, but no endpoint anywhere consumes that token to let the invitee actually set a password and activate the account — confirmed by grep (`app/modules/`) finding no route touching `InvitationToken`'s consumption path outside `admin_users` itself (which only invalidates/reissues, never consumes-to-activate). This isn't a §7 violation (no credential is mishandled — the account simply can't authenticate at all yet), but it's worth flagging: an invited user has no way to complete setup until a follow-up story builds that flow, matching the source story's own scope boundary but worth confirming is tracked.
- **[Low] `resend_invite`'s 403 path is not itself audited on the *insufficient-permission* branch beyond the shared `require_scope` mechanism.** MU-AC21 states "an actor without `users:write`... the denied attempt is audited" — this is satisfied entirely by the pre-existing, already-audited `auth_audit_log(event=authz_denied)` write inside `require_scope`'s dependency (`roles/dependencies.py`, unchanged by this story), not by anything `admin_users` itself writes. Confirmed correct, not a gap — noted only so a future reader doesn't go looking for a second audit write inside `admin_users/service.py` that was never meant to exist.

## Verdict Rationale

Pass: all six `AGENTS.md` §7 rows check out clean, with the story's near-total absence of credential handling making rows 1, 2, and 6 straightforward rather than requiring invented justification — the one credential-adjacent decision this story does make (`hashed_password=""` for a newly invited account) was verified safe by construction, not assumed.
