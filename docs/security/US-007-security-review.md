# Security Review: US-2.3 Refresh Token

**Story ID:** US-007
**Reviewed:** 2026-09-01
**Overall Verdict:** Pass

## Summary

Reviewed US-2.3's implementation against AGENTS.md §7's six non-negotiable rules. This story handles no password verification, introduces no new inbound schema (cookie-only credential), adds no raw SQL, adds no sensitive logging, and preserves a uniform `token-invalid` response shape across every rejection branch. All six checks pass clean. Given US-2.2's own post-Pass IDOR (an unchecked cross-user ownership match), this review also specifically analyzed whether an analogous ownership gap exists in this story's reuse-detection/rotation logic — see the dedicated section below — and found none: unlike logout, refresh has only one credential in play (the refresh token itself), so there is no second identity signal to cross-check against.

## Ownership / cross-user analysis (prompted by US-2.2's post-Pass IDOR)

US-2.2's own security review found that `logout()` trusted a hash-matched `refresh_tokens` row without checking it belonged to the caller identified by a *separate* credential (the Bearer access token) — two credentials were in play, and only one was checked against the other.

`rotate_refresh_token` has no analogous two-credential structure: the refresh token presented in the cookie **is** the sole credential, and its own `user_id` (`existing.user_id`, read from the row the token's hash resolves to) is the only identity the method ever acts on — used consistently for the account-eligibility check (`service.py:592-596`), the new session (`create_session(user_id=consumed.user_id, ...)`, `:625-627`), the new access token (`encode_access_token(user_id=consumed.user_id, ...)`, `:637`), and the reuse-alert email recipient (`get_by_id(token.user_id)`, `:678`). There is no second, independently-supplied identity anywhere in this method for that value to be checked against — unlike `logout()`, which received both an authenticated caller's `user_id` *and* a separately-resolved refresh-token owner and had to reconcile the two. Since possession of the raw, cryptographically-random token value is itself the only authorization signal this endpoint recognizes (by design — this is what "the refresh cookie is the credential" means), there is no ownership check to omit here.

## Advisory Findings (non-§7, does not force Fail)

- **[Low] CSRF protection is not enforced.** `POST /v1/auth/refresh` is a cookie-authenticated, state-changing endpoint, and no CSRF mechanism exists anywhere in this codebase — same standing gap US-2.2's own security review flagged (tracked there as a follow-up from resolved OD-4). Not new to this story, not re-litigated here.
- **[Low] Unknown/never-issued token values are not rate-limited.** OD-1's 60/family/hour limit is keyed by `family_id`, which only exists once a presented token resolves to a real row (`service.py:544-551`) — a token that never matches any `refresh_tokens.token_hash` at all skips this check entirely, since there is no `family_id` to key it on. Given the token's 256-bit entropy (`secrets.token_urlsafe(32)`), brute-forcing a valid value by repeated guessing is computationally infeasible regardless of rate limiting, and this scope was explicit in the resolved OD-1 decision ("a client hammering a *real* family"), not an oversight. Flagged for visibility, not a defect.
- **[Low] The paired access token survives family revocation for up to 15 minutes on reuse (resolved OD-6).** Already a disclosed, user-accepted tradeoff in the spec (no `family_id` link from `user_sessions`) — restated here only because it is the kind of blast-radius question a security review specifically exists to surface, not because it's an undisclosed gap.

## Verdict Rationale

Pass: all six §7 rows are Pass or a genuinely-applicable N/A, with cited evidence for each. The ownership/IDOR-analog analysis prompted by US-2.2's own post-Pass finding surfaced no equivalent gap — refresh's single-credential design has no second identity to reconcile against. All three advisory items are disclosed, already-accepted tradeoffs from the spec/prior stories, not new or hidden defects, and none affects any of the six non-negotiable rules this skill enforces.
