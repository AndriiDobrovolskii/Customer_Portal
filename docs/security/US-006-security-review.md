# Security Review: US-2.2 Logout

**Story ID:** US-006
**Reviewed:** 2026-08-31
**Overall Verdict:** Pass

## Summary

Reviewed US-2.2's implementation against AGENTS.md §7's six non-negotiable rules. This story touches no password-handling code at all (logout has no credentials to verify), introduces no new inbound schema, adds no raw SQL, adds no new logging, and preserves a uniform, generic `401` shape across every auth-failure branch on both routes. All six checks pass clean.

## Advisory Findings (non-§7, does not force Fail)

- **[Low] CSRF protection is not enforced on either route.** `POST /v1/auth/logout` and `POST /v1/auth/logout-all` are both cookie-authenticated (via the `Authorization` header today, but the story's own NFR calls out CSRF because a browser client would rely on the ambient refresh cookie), state-changing endpoints, and no CSRF mechanism exists anywhere in this codebase. This is not a new gap introduced by this story — it's the explicit, user-approved resolution of OD-4 (`docs/decisions/US-2.2-open-decisions.md`), disclosed in the spec's Out of Scope section and tracked as a follow-up. Not a §7 violation (CSRF isn't one of the six enumerated non-negotiables) and not re-litigated here, but flagged for visibility since it's a real, live gap in the deployed surface until the follow-up story lands.

## Addendum (2026-09-01): IDOR found and fixed post-Pass

An independent review after this report was first issued found a real gap this checklist's six §7 rows don't cover: none of them is "authorize the object a lookup returns," and LO-AC1's own wording ("the presented refresh token is marked revoked") is silent on whether the presented token must belong to the caller.

`UserService.logout()` (`app/modules/users/service.py`, in the `logout()` method) looked up a presented refresh cookie by hash via `get_refresh_token_by_hash()` — which matches *any* user's row — and revoked that row's rotation family without comparing the row's `user_id` to the authenticated caller's `user_id`. Concretely: an attacker with their own valid access token who obtained any victim's raw refresh-token value could set it as their own `refresh_token` cookie, call `POST /v1/auth/logout`, and silently revoke the victim's entire refresh-token family — a cross-user session kill returning a clean `204`, with no error differentiating it from an ordinary lookup-miss.

**Fixed same-day:** the family-revocation branch now requires `existing.user_id == user_id` in addition to a hash match (`app/modules/users/service.py`, `logout()`). A cross-user match is now treated identically to a lookup-miss — silent skip, still `204` — preserving the exact anti-enumeration property LO-AC4 already required for the stale-cookie case. Two new tests added: `test_logout_cross_user_refresh_cookie_does_not_revoke_other_users_family` (unit, `tests/unit/modules/users/test_users_service.py`) and its integration counterpart of the same name (`tests/integration/modules/users/test_users_router.py`), both asserting the victim's `refresh_tokens.revoked_at` stays `NULL` after the attacker's call. Full suite reverified: 186/186 pass, mypy strict clean, `pre-commit run --all-files` green.
