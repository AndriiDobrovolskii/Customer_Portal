## Known Constraints

- Permission scopes are enforced through the `roles` module; every
  administration endpoint checks a scope rather than a role name directly.
- The audit chain is append-only and hash-linked. `audit_log_history` is a raw
  SQL `UNION ALL` view, deliberately not ORM-mapped.
- Personal-data erasure is handled by `scripts/anonymize_erased_user.py`
  (anonymization, not hard deletion) so the audit trail survives account
  erasure.
- The cache is never the source of truth: reads degrade to PostgreSQL on a miss
  or outage. The token denylist is the one exception and fails closed.
- `tickets.category` has no DB-level `CHECK`/`ENUM` constraint yet — allowed
  values are an open stakeholder decision (US-4.1 OD-3). Any category-specific
  logic in a future story must not assume a fixed value set.
- `ticket_number` (format `CP-{year}-{seq:07d}`) is sequentially guessable via
  a plain SEQUENCE — acceptable today because no endpoint looks it up, but a
  future story must not add a `ticket_number`-keyed lookup without revisiting
  this (US-4.1 Spec Drift, Low security advisory).
- The application's own request-serving DB connection runs through a
  dedicated non-superuser `app_runtime` role (provisioned by
  `scripts/db/provision_runtime_role.sql`), separate from the superuser role
  Alembic migrations still use. This is load-bearing for Row-Level Security —
  the previously-single configured role is a PostgreSQL superuser and
  unconditionally bypasses RLS. A future story adding a table/column reached
  through the normal request path must confirm the provisioning script's
  `GRANT`s still cover it (proven only by a full-suite regression run, not by
  inspection — US-4.2 Architectural Change #12, Risk 7). Documented in
  `docs/ARCHITECTURE.md` §3.6 (applied 2026-09-07, during the US-4.3 archive
  run, alongside US-4.3's own proposal below).
- BR-017 (auto-close / reopen-on-reply, shared 7-day boundary) is now fully
  shipped: the reply-side reopen landed in US-4.2, and the auto-close job
  (`scripts/auto_close_resolved_tickets.py`) plus direct `/resolve`, `/close`,
  `/reopen` endpoints landed in US-4.3. No scheduler currently invokes the
  auto-close script — running it on a cadence is an ops decision, not yet
  made.
- The status-transition endpoints (`/resolve`, `/close`, `/reopen`) all route
  through one race-safe `TicketRepository.transition_status(...)` conditional
  `UPDATE` (status, and for reopen paths the 7-day window, embedded in the
  `WHERE` clause; no row lock) — documented in `docs/ARCHITECTURE.md` §4.9
  (applied 2026-09-07). A future story adding another ticket-status-mutating
  endpoint should reuse it rather than a separate read-then-write path.
- Two documented, non-blocking gaps carried forward from US-4.3: the response
  for a resolved-but-expired-not-yet-auto-closed ticket is undefined by any FR
  (falls through to `409`); the `/close`/`/reopen` `reason` field is accepted
  but unconstrained and unpersisted.
- `docs/product/business-rules.md` gained BR-018 (US-4.2 reply status
  transitions) and BR-019 (US-4.3 resolve/close/reopen rules), applied
  2026-09-07 alongside this file's own update.
- `assignee_id` (US-4.4) is exposed only via two new schemas
  (`AgentTicketRead`, `AgentTicketStateRead`) scoped to the agent-facing
  queue and assign/unassign endpoints — the shared customer-visible
  `TicketRead`/`TicketStateRead` (US-4.1/US-4.3) are untouched and must stay
  that way. `assign_ticket`'s two `422` branches (nonexistent/non-agent
  target vs. deactivated target) use distinguishable message text, which lets
  a `tickets:write` holder enumerate a deactivated agent account (Low/Medium,
  staff-only audience, non-blocking) — a future story touching this endpoint
  should collapse them to one shared message.
- US-5.1 is the first delivery on the frontend track (`frontend/`, React +
  Vite + TS). Nine Open Decisions remain OPEN, carried forward: most
  notably, `app/main.py`'s CORS middleware does not cover a Vite dev-server
  origin and lacks `allow_credentials=True` — if a future story resolves
  this toward an actual backend CORS change (rather than a same-origin dev
  proxy), that story must treat `app/main.py` as newly in scope. The access
  token is held in memory only (never persisted); the refresh token is an
  `httpOnly` cookie the frontend never reads or parses. Concurrent-401
  refresh calls are serialized through a single-flight coordinator to avoid
  BR-008's refresh-token-reuse/family-revocation trap.
- US-5.2's profile *view* (PS-AC1) is not implemented — no `GET /profile` or
  `GET /users/me` endpoint exists yet, so `ProfileScreen.tsx` ships
  write-only until a future backend Story adds the read endpoint (OD-5,
  OPEN). `httpClient.ts` gained an additive `httpPatch<T>` returning
  `{data, status, headers}` so callers can read `ETag`; it re-implements its
  own 401-refresh-retry branch independently of the pre-existing one in
  `performRequest` — both correct and tested today, but a future story
  touching either should collapse them to one shared implementation. Three
  Open Decisions remain OPEN, each designed around with a recorded default
  rather than resolved: OD-3 (no forced navigation on an enrollment-scoped
  token's `403`, banner-link-only), OD-6 (locale list is a two-item
  placeholder, `en-US`/`en-GB`, via one shared `SUPPORTED_LOCALES`
  constant), OD-7 (timezone input uses the full runtime
  `Intl.supportedValuesOf("timeZone")` set, not a curated subset).
