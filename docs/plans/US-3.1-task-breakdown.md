## Notes

- T1/T2/T2b/T4 run in parallel — none depends on any of the others. T4 (roles' cross-module integration) is genuinely independent of this story's new schema: `check_no_privilege_escalation`/`raise_if_last_admin` operate on the existing, unchanged `roles`/`permissions`/`role_permissions`/`user_roles` tables, not on anything T2/T2b/T3/T3b add.
- **`migrations/env.py`'s model-registration line is deliberately unassigned to any execution skill** (`docs/reviews/plans/US-3.1-plan-review.md` Risk Realism finding, corrected 2026-09-02) — neither `data-layer-builder` (scoped only to a module's own `models.py`/`repository.py`/`cache.py`) nor `migration-manager` (explicitly excludes this file) declares this in scope, matching how US-3.2's identical registration was actually handled (an out-of-band, user-approved step, not part of that story's own plan). Execution requests explicit sign-off at this point in the sequence, before T3.
- **T4's `raise_if_last_admin` stays unwired from `replace_user_roles`, corrected 2026-09-02 (advisor cross-check during plan-review).** An earlier draft had `replace_user_roles` calling both new `RoleService` methods; `raise_if_last_admin`'s trigger condition (target holds admin and is the last one) is broader than what `replace_user_roles` actually needs (only when admin is being removed from the set), so wiring it in would have rejected a role change that succeeds today (`{admin}` → `{admin, auditor}` for the sole admin). Only `check_no_privilege_escalation` is a true extraction; `raise_if_last_admin` is additive-only, called from `admin_users/service.py` (T5) alone.
- **T3/T3b split, corrected 2026-09-02 (plan-review finding).** The original single-migration T3 bundled a `CREATE INDEX CONCURRENTLY` build with ordinary transactional DDL, contradicting this project's own US-2.6 precedent (two migrations: one for columns, one "deliberately alone" for the concurrent index, per that migration's own docstring). T3 now covers only `invitation_tokens` + the 5 nullable audit columns + the ordinary `(status, created_at)` index; T3b, depending on T3, covers the `pg_trgm` extension and the concurrent trigram index alone.
- T4 is scoped separately from T5/T6 even though all three use `service-and-router-builder`, because T4 modifies a **different module's** already-shipped `service.py` (`roles`, not `admin_users`) — mirrors US-3.2's T4/T6 split and US-2.5's T4/T5 split for the identical reason: keeping a cross-module dependency visible in the sequence rather than buried inside the new module's own task.
- T2b bundles two different modules' `models.py` files (`roles`, `account`) into one task rather than splitting further, since both are simple independent nullable-column additions with no shared logic and no dependency on each other — unlike T4/T5/T6's genuine cross-module service dependency, there's nothing here for a split to make visible.
- The plan's Architectural Change #4 (`UpdateUserRequest` gains required `reason`) is already reflected in `US-3.1-openapi.yaml` (amended by `planner`) — T1 implements it directly, not a decision T1 makes itself.
- The remaining `US-3.1-api-design.md`/`US-3.1-db-design.md` gaps not resolved by the plan (list-envelope field names, cursor encoding, `limit`'s max, 412/429 slug-naming rationale) are **not** separate tasks — they're implementation-detail choices T1/T2/T5/T6 make directly and document inline, mirroring how US-3.2/US-2.5 handled their own carried-forward gaps, since none of them changes this task sequence's shape.
- `tests/conftest.py`'s fixture extensions are scoped to T8 (integration), not a separate task, matching the US-2.4/US-3.2/US-2.5 precedent.
