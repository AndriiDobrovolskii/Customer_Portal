## Notes

- T1/T2/T2b run in parallel — none depends on either of the others.
- **`app/core/*` files (crypto.py, security.py, cache_keys.py, config.py, .env.example) are scoped to T5, not T2** — following the corrected precedent from `docs/plans/US-3.2-task-breakdown.md`'s own Notes: `data-layer-builder` may only touch a module's own `models.py`/`repository.py`/`cache.py`, never `app/core/*`; these five files land under whichever service task is their first actual consumer, which is T5 (`users/service.py`'s MFA logic and token issuance).
- T4 is scoped separately from T5 even though both use `service-and-router-builder`, because T4 modifies a **different module's** existing `service.py` (`roles`, not `users`) — mirrors US-3.2's T4/T6 split for the same reason (making the cross-module dependency visible in the sequence, not buried inside a single module's task).
- T2b (roles' `list_role_grants_for_user`/`granted_at` write) is a data-layer change to an **already-merged, already-shipped** module (US-3.2) — not new module scaffolding. It's still `data-layer-builder`'s job (the layer being touched, not the module's age, determines the skill), but flagged here so the task isn't mistaken for greenfield roles work.
- The three items carried forward from `US-2.5-api-design.md`'s Open Questions (activate's error-shape distinction, whether `DELETE /v1/auth/mfa` accepts a recovery code, disable's check-precedence order) are **not** separate tasks — they're implementation-detail decisions T5/T6 make directly and document inline (mirroring US-3.2's T4/T5 handling of its own carried-forward gaps), since none of them changes this task sequence's shape.
- `tests/conftest.py`'s fixture extensions (MFA state, role-grant timestamp) are scoped to T8 (integration), not a separate task — matching the US-2.4/US-3.2 precedent of folding `conftest.py` changes into whichever test task first needs them.
