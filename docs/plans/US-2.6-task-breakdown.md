## Notes

- T1, T2, T4 run in parallel — none depends on either of the others.
- **`app/core/geoip.py`/`device.py`/`config.py` are scoped to T4, a dedicated task, not folded into T2 (`data-layer-builder`)** — following the corrected precedent from `US-2.5-task-breakdown.md`'s Notes: `data-layer-builder` may only touch a module's own `models.py`/`repository.py`/`cache.py`, never `app/core/*`. Unlike US-2.5 (where the `app/core/*` additions landed inside the single service task, T5, as its first actual consumer), this story gives them their own task because two *independent* new primitives (geo-IP, device-label) with no shared internal dependency are cleaner to verify (and to gate on their own fallback-behavior tests) before `service.py` composes them, rather than bundling primitive-writing and composition into one task.
- T3 depends only on T2, not T4 — the migration touches `refresh_tokens`/`auth_audit_log` only; `app/core/*` has no schema footprint.
- `pyproject.toml`'s two new dependencies (`user-agents`, `geoip2` — user-approved 2026-09-02) are added as part of T4, the first task that imports them.
- The GeoLite2 `.mmdb` fetch-at-build-time step (user-approved 2026-09-02) is a deploy-pipeline/CI concern, not an application-code task in this breakdown — `app/core/geoip.py` (T4) only needs to handle the file's absence gracefully, which is already a stated verification condition on T4.
- `tests/conftest.py` fixture extensions (if any are needed for the concurrent-login test's two-connection setup) are folded into T8, matching the US-2.4/US-2.5/US-3.2 precedent of scoping `conftest.py` changes to whichever test task first needs them.
- FR-7 (cap eviction) has no dedicated task of its own — it's part of T5's service-layer scope (login-path extension) and T7/T8's test scope, per `US-2.6-implementation-plan.md`'s Architectural Change #3 explicitly calling out that this is a login-flow change, not new sessions-only work.
