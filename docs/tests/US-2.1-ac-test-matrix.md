## Note on T7 (deviation found during IMPLEMENTATION)

The task breakdown originally planned T7 as a new `tests/unit/modules/users/test_users_cache.py` unit-testing `LoginThrottleCache` against a mocked Redis client. Checking precedent during implementation: `RevocationCache` (US-1.4's own Valkey gateway) has no unit test file anywhere in this codebase — every existing cache gateway is exercised only via a hand-written `Protocol` fake at the service-test level (already covered here by `FakeLoginThrottleCache` in `test_users_service.py`) and proven for real via integration tests. `AGENTS.md` §5 also states unit tests have "no DB, no Valkey, no network." Mocking the Redis client to unit-test `LoginThrottleCache` would both violate that rule and deviate from the established pattern. T7 was dropped; `LoginThrottleCache`'s real behavior (atomic increment, TTL) is verified for real by `test_login_account_throttled_returns_429` in T8 instead.

## Note on TESTS-before-IMPLEMENTATION sequencing

Same deviation `US-1.4-traceability-matrix.md` already recorded and justified: `docs/workflow/stage-map.yaml` places `TESTS` before `IMPLEMENTATION`, but this story's task breakdown (`docs/plans/US-2.1-task-breakdown.md`) sequences test tasks (T6, T6b, T7, T8) *after* their corresponding service/router/cache tasks (T4, T4b, T2, T5), because the unit/integration tests import `UserService`, `AccountService.reactivate_account`, the new `cache.py` gateway, `AuthAuditLog`, and `RefreshToken` by name — none of these exist until the execution skills create them. This matrix is TESTS's actual deliverable; the test *files* land per the task breakdown's ordering.
