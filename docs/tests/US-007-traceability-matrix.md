## Note on the AGENTS.md §5 security-baseline pattern

Every other authenticated route in this project's traceability matrices lists four uniform security-baseline cases (no token / malformed / expired / revoked). `POST /v1/auth/refresh` is not behind `CurrentUserDep`/`OAuth2PasswordBearer` at all (per `US-007-api-design.md`) — its sole credential is the refresh cookie, and "no cookie," "malformed cookie value," "expired," and "revoked-by-logout" are already exactly RT-AC3's three cases plus the missing-cookie sub-case (all indistinguishable `401 token-invalid` responses per resolved OD-3). No separate baseline rows are added; RT-AC3's rows above already are the baseline for this endpoint.

## Note on TESTS-before-IMPLEMENTATION sequencing

Same deviation `US-005-traceability-matrix.md`/`US-006-traceability-matrix.md` already recorded and justified: `docs/workflow/stage-map.yaml` places `TESTS` before `IMPLEMENTATION`, but this story's task breakdown (`docs/plans/US-007-task-breakdown.md`) sequences the test tasks (T6, T7) *after* their corresponding service/router tasks (T4, T5), because the unit/integration tests import `UserService.rotate_refresh_token`, `UserRepository.consume_refresh_token`, `RefreshRateLimitCache`, and the new model columns by name — none of which exist until the execution skills create them. This matrix is TESTS's actual deliverable; the test *files* land per the task breakdown's ordering.
