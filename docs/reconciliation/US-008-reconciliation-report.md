# Reconciliation Report: Password Reset (US-2.4 / spec US-008)

**Story ID:** US-2.4
**Reviewed:** 2026-09-01
**Overall Verdict:** Pass

## Summary

All six Acceptance Criteria (PR-AC1–PR-AC6) have a traceability-matrix row, an existing, behavior-asserting test at both the unit and integration level, and no confirmed drift from the approved spec (`docs/specifications/US-008-password-reset-spec.md`). Two matrix-accuracy gaps were found and fixed during this review — five test function names went stale after being renamed during T6 for line-length, and one test the code actually needs (an "unverified account" eligibility case) was missing from the original matrix — both corrected before this report. One implementation-time interpretation, not literally required by any AC, is disclosed under Spec Drift as Low severity; it doesn't change the verdict.

## Spec Drift

- **[Low] Password-reset eligibility silently extended to exclude unverified accounts, beyond what any AC states** — Spec's FR-1/FR-3 (and the source story's own PR-AC1/PR-AC3) speak only of "registered, active account" vs. "not registered, or belongs to a deactivated account" — neither mentions an unverified (email not yet confirmed) account as a third category. The shipped service (`app/modules/users/service.py:request_password_reset`, `eligible = user is not None and user.status != UserStatus.DEACTIVATED.value and user.email_verified`) treats an unverified account identically to a deactivated one — no token, no email, but still the identical 202 response. This was a reasoned implementation-time decision (mirroring login's own eligibility notion — an unverified account can't log in yet either, so a reset wouldn't unblock anything) rather than a contradiction of stated behavior, and is transparently documented in the service's own docstring and this story's traceability matrix — but it is genuinely new behavior no AC or FR literally requires, so it's flagged here for visibility rather than silently folded into "Pass."

## Verdict Rationale

Pass: all six ACs have full matrix coverage, every referenced test exists (verified by direct `grep` against both test files, not assumed from the matrix), and every test asserts the AC's actual stated behavior rather than merely touching the same endpoint — several integration tests (PR-AC2's revocation proof via protected-route probes, PR-AC3's byte-identical-body assertion, PR-AC5's actual-retry proof) go beyond the minimum bar. PR-AC4's "password remains unchanged" sub-clause is only implicitly covered (no repository write occurs before any of its three rejection paths) rather than independently asserted — worth tightening but not severe enough on its own to force "Pass with Issues," per this review's read of the assertions' actual strength. The one Spec Drift finding is a disclosed, reasoned addition with no externally-visible contract change (still 202, still generic body) — not a violation of any stated AC.
