# Reconciliation Report: Multi-Factor Authentication / TOTP (US-2.5 / spec US-009)

**Story ID:** US-2.5
**Reviewed:** 2026-09-02
**Overall Verdict:** Pass (7 gaps found and closed same-day)

## Summary

All 7 source ACs (MF-AC1–MF-AC7) and FR-8 (the no-AC disable path) have at least one existing, behavior-asserting test — no AC is left with zero coverage. However, cross-checking every test function name the pre-implementation traceability matrix commits to against the actual test files (not just the matrix's own claims) surfaced two classes of discrepancy. The first is harmless: roughly a dozen matrix rows name a test function that was renamed during T7/T8 (e.g. the matrix's `test_login_*` family shipped as `test_authenticate_user_*`, matching the service method rather than the route) — in every one of these cases the renamed test was located and its assertions confirmed to match the AC, so these are matrix-documentation drift, not coverage gaps, and are not counted below. The second was real: **7 test functions the matrix names did not exist anywhere, under any name**, and the behavior they were meant to prove was genuinely unasserted by any other test. All 7 were closed same-day (6 new tests, one gap resolved by a test written for another gap) — see Gaps Closed below. No code change was needed for any of them; two were independently re-verified as correct-but-untested before writing their tests.

No AC-level spec drift was found. One divergence was checked explicitly because it originated in this session's own SECURITY_REVIEW fix (`disable_mfa` now raises a single `InvalidCredentialsError` for both a wrong password and a wrong code, where it previously raised a distinct `MfaInvalidCodeError` for the latter) — see Spec Drift below; it is not drift, since the API design never committed `DELETE /v1/auth/mfa`'s 401 to the `mfa-invalid-code` slug in the first place.

## Gaps Closed (test named in the matrix did not exist anywhere, under any name)

Ranked by consequence. All 7 closed same-day; none required a code change.

1. **[Most consequential] `test_replace_for_user_sets_granted_at_explicitly`** — no test at any level (unit or integration) proved `roles/repository.py::replace_for_user` actually writes `granted_at = func.now()` on a role grant. This column is FR-6's *entire data source* for the 14-day rollout grace-period clock; a regression here (e.g. a future edit that drops the explicit write and relies on the column's default, or that stops writing it on a *repeat* grant) would silently mis-time every privileged user's enrolment deadline with no test catching it. **Closed:** `tests/integration/modules/roles/test_roles_router.py::test_replace_user_roles_sets_granted_at_to_recent_value` seeds the target already holding the role with a 30-day-stale `granted_at`, re-grants it via `PUT /v1/admin/users/{id}/roles`, and confirms the persisted value moved to recent — proving the explicit per-call overwrite (a full replacement, not an upsert-if-changed) that the column's own docstring comment claims. Real DB round trip, not a fake.
2. **`test_enroll_mfa_accepts_enrollment_scoped_token`** — FR-6 names `POST /v1/auth/mfa/enroll` and `POST /v1/auth/mfa/activate` as the two endpoints an enrolment-scoped token remains valid against. Both full-flow integration tests exercised the scoped token against `activate` only. **Not a live bug**: `app/modules/users/router.py:174-176` independently re-confirmed `enroll_mfa` already depends on `CurrentUserAllowEnrollmentScopedDep` before writing the test. **Closed:** `tests/integration/modules/users/test_mfa_router.py::test_enroll_mfa_accepts_enrollment_scoped_token`.
3. **`test_disable_mfa_rejects_enrollment_scoped_token`** — the matrix's own row for this test explicitly calls out `DELETE /v1/auth/mfa` as "NOT in the enrollment allow-list," distinct from the two endpoints that are. The only "scoped token is rejected elsewhere" proof in either full-flow test targeted `POST /logout-all` (an arbitrary unrelated route), never `DELETE /mfa` specifically — the one MFA-adjacent route a future maintainer is most likely to mistakenly add to the allow-list by analogy. Router code independently confirmed `disable_mfa` correctly uses the plain `CurrentUserDep`. **Closed:** `tests/integration/modules/users/test_mfa_router.py::test_mfa_disable_rejects_enrollment_scoped_token` (asserts `403 mfa-enrollment-required`) — this also closes gap 7 below, since it's the second concrete route this story's allow-list mechanism is now proven against.
4. **`test_verify_mfa_wrong_recovery_code_counts_toward_totp_lockout`** (OD-10) — the only lockout-counter test submitted the same wrong TOTP-shaped code (`"000000"`) all 5 times; no test ever submitted a wrong recovery-code guess to prove it shares the counter. Read `verify_mfa`'s control flow (`app/modules/users/service.py:1272-1309`) before writing the test: a failed `_try_consume_recovery_code` unconditionally falls through to the same `record_failed_attempt` call a failed TOTP check reaches — confirmed correct, not just assumed. **Closed:** `tests/unit/modules/users/test_users_service.py::test_verify_mfa_wrong_recovery_code_counts_toward_totp_lockout`.
5. **`test_login_both_scoping_triggers_true_issues_single_scoped_token`** — `_resolve_enrollment_scoping` (`app/modules/users/service.py:415-446`) checks `mfa_reenrollment_required` first and returns before ever consulting role grants, so the two triggers cannot actually double-fire by construction — but that precedence itself was unverified. **Closed:** `tests/unit/modules/users/test_users_service.py::test_rotate_refresh_token_both_scoping_triggers_true_issues_single_scoped_token` seeds both conditions simultaneously true and asserts the token is scoped with no deadline leaking in from the (never-reached) role-grant branch.
6. **`test_mfa_verify_skew_and_replay_with_fixed_clock`** (integration) — `MfaReplayCache.mark_step_used`'s real behavior (a Valkey `SET NX`, per `app/modules/users/cache.py`) was only ever exercised against a hand-written fake in unit tests. Checked for a documented deferral matching this story's own precedent (the `db_session` single-transaction limitation cited in `test_full_enrollment_scoping_flow_role_grant_to_resolution`'s trailing comment) — none existed near this test or anywhere in the file; this was an undisclosed gap, not a disclosed scope reduction. **Closed:** `tests/integration/modules/users/test_mfa_router.py::test_verify_mfa_replayed_code_rejected_against_real_valkey` — logs in twice (two separate `mfa_token`s), submits the same TOTP code to both, and confirms the second is rejected against the real Valkey backend.
7. **`test_only_enroll_and_activate_routes_use_enrollment_scoped_dependency`** — was **Partially Covered**, not fully missing: `test_full_enrollment_scoping_flow_role_grant_to_resolution`'s Act 2 already proved one other route (`POST /logout-all`) rejects a scoped token. Rather than invent a new architecture-test convention this codebase doesn't otherwise have (no existing static-source-sweep test file), gap 3's fix above was judged sufficient: it adds `DELETE /mfa` as a second, more targeted data point (the specific route closest to being mistakenly included), giving two independent HTTP-level proofs of the allow-list boundary. `grep -rn "CurrentUserAllowEnrollmentScopedDep" app/` confirms only 2 usages exist in the whole codebase (`router.py`'s `enroll_mfa`/`activate_mfa`), both now covered.

## Spec Drift

No AC-level drift found. One point was checked explicitly because it changed during this session's SECURITY_REVIEW stage: `disable_mfa`'s wrong-code path now raises `InvalidCredentialsError` (401) instead of the previous `MfaInvalidCodeError` (401) — same status code, different exception type/slug, fixed to close a factor-distinguishing oracle (`docs/security/US-009-security-review.md`). Checked against `docs/designs/api/US-009-openapi.yaml:149-152`, which documents `DELETE /v1/auth/mfa`'s 401 as "No valid access token, OR `current_password`/`code` is wrong. **Cross-cutting shape, reused.**" — the API design never committed this endpoint's wrong-code case to the `mfa-invalid-code` slug in the first place (unlike `verify`'s 401, which explicitly does, per line 111). The fix's outcome — a generic, reused 401 shape — is exactly what the original contract already called for; the code briefly diverged from its own design during initial implementation, and SECURITY_REVIEW's fix brought it back into alignment. Not drift.

## Verdict Rationale

Pass: all 7 source ACs plus FR-8 have full, verified matrix coverage after closing the 7 gaps found during this review. Each gap was independently investigated before writing its test — two (`enroll` accepting, `disable` rejecting a scoped token) were confirmed as pre-existing-correct-but-untested by reading the actual router wiring, not assumed; one (OD-10's shared counter) was confirmed correct by reading `verify_mfa`'s control flow before asserting it; one (the both-triggers case) was confirmed to be a short-circuit-by-construction, not an actual combinatorial risk, before writing a test that still verifies the precedence holds. The most consequential gap — `granted_at`'s write path going completely unverified, despite being FR-6's sole grace-period-clock data source — is now covered by a real-database test, not a fake. 6 new test functions were added (`tests/integration/modules/roles/test_roles_router.py` ×1, `tests/integration/modules/users/test_mfa_router.py` ×3, `tests/unit/modules/users/test_users_service.py` ×2); the 7th gap was resolved by one of those additions rather than needing a dedicated new test. Full suite re-verified green after every addition: `pre-commit run --all-files` 7/7, `pytest --cov` 367/367 passing, 97.35% coverage (up from 361/97.35% before this review). No AC-level spec drift found. This report advances the story to PR.
