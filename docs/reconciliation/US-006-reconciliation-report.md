# Reconciliation Report: US-2.2 Logout

**Story ID:** US-006
**Reviewed:** 2026-08-31
**Overall Verdict:** Pass

## Summary

Every Acceptance Criterion (LO-AC1–LO-AC5) has a traceability-matrix row, and every referenced test function exists and was opened and read. One gap was found: LO-AC4's integration test (`test_logout_repeat_call_same_token_returns_204_idempotent`) verified the `204` status and empty body but never asserted LO-AC4's explicit "no additional revocation side effects occur" clause. Fixed same-day: the test now also asserts `user_sessions.revoked_at` is bit-for-bit unchanged between the first and second `/logout` calls (not silently re-written), stable across 3 reruns and the full 184-test suite. No spec-vs-shipped-code drift was found; the OD-1–OD-6 mechanism substitutions are all disclosed and traced, not silent departures.

## Spec Drift

None found. Every place the shipped code's behavior differs from the *story's* literal wording (Valkey denylist → `user_sessions.revoked_at`; the LO-AC4/LO-AC5 leniency scoping) is a disclosed, user-approved resolution already traced through `docs/decisions/US-2.2-open-decisions.md` → the revised `docs/specifications/US-006-logout-spec.md` → the implementation — not something introduced silently during coding. No field was renamed, no validation rule loosened, and no status/error code changed from what the approved spec and API design (`docs/designs/api/US-006-openapi.yaml`) state.

## Verdict Rationale

Pass: full AC coverage (5/5 have matrix rows and existing, behavior-asserting tests) and no spec-vs-code drift. The one gap found (LO-AC4's test not independently verifying "no additional revocation side effects") was fixed in this same review pass — the test now asserts persisted `user_sessions.revoked_at` is unchanged across the repeat call — and reverified stable. Also noted, not a finding: `docs/tests/US-006-traceability-matrix.md`'s security-baseline "Expired token" row still pointed at `test_logout_invalid_token_returns_401` after a dedicated expired-token test was added during VERIFICATION; corrected in the same pass.

## Addendum (2026-09-01): LO-AC1 reconciled against ownership, not just hash-match

A post-Pass independent review found that LO-AC1's own literal text — "the presented refresh token is marked revoked" — is silent on *whose* token, and the shipped code (before this addendum) revoked a hash-matched family regardless of which user's row it was, an IDOR (full detail in `docs/security/US-006-security-review.md`'s own 2026-09-01 addendum). Fixed same-day in `app/modules/users/service.py`'s `logout()`. The traceability matrix gained two new rows for the ownership-check regression tests (see `docs/tests/US-006-traceability-matrix.md`). This does not change the verdict here — LO-AC1's matrix row and test already existed and asserted the AC's stated behavior faithfully; the AC's own wording simply didn't state the ownership constraint explicitly, so this was a code defect caught by an out-of-band review, not a reconciliation gap in this report's original pass.
