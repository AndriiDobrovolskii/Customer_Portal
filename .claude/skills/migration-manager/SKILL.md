# Migration Manager

## Purpose

Turn a `models.py` change into a safe, idempotent Alembic migration. The `Rewriter` in `migrations/env.py` only reaches autogenerated create/drop table/index directives — everything else in a real migration (column adds, altered types, hand-written DDL, backfills) needs a guard this skill is responsible for adding, and the only real proof any of it works is actually running the upgrade/downgrade/upgrade cycle, not asserting that it would.

## Operational Contract

```
Precondition: data-layer-builder has already changed models.py for this story; a reachable PostgreSQL database exists to run alembic commands against.
Input Artifacts: the module's changed app/modules/<module>/models.py; migrations/versions/ (existing revisions); migrations/env.py (read-only).
Output Artifacts: one new migrations/versions/<hash>_<description>.py file; the real captured upgrade→downgrade→upgrade command output, quoted in the chat report.
```

## Required Context

Read, in order:

1. The module's already-changed `models.py` — this skill does not decide the schema, only migrates to it.
2. `migrations/versions/` — especially `migrations/versions/2c77dd65027b_add_profile_and_auth_foundation.py`, the canonical in-repo exemplar of the `sa.inspect(op.get_bind())` guard pattern, `if_not_exists=True`/`if_exists=True` on autogenerated ops, a guarded hand-written `op.execute()` (the append-only trigger), and a real, symmetric `downgrade()`.
3. `migrations/env.py` — read-only. Understand exactly what the `Rewriter` does (`_add_if_not_exists`/`_add_if_exists`, applied only to `CreateTableOp`/`CreateIndexOp`/`DropTableOp`/`DropIndexOp`) so you know precisely what it does *not* reach.
4. `AGENTS.md` §4 — the "Migrations" bullet and its PostgreSQL-specific hazards paragraph.

## Preconditions

`models.py` already reflects the target schema — this is not a design or model-writing skill (that's `data-layer-builder`). A database must be reachable to actually run `alembic` commands; if not, stop and report that rather than fabricating command output.

## Workflow

1. **Generate.** `alembic revision --autogenerate -m "<snake_case_description>"` — a real, specific description of the change (e.g. `add_mfa_totp_secret_to_users`), never a generic placeholder.
2. **Read the generated file in full** before trusting anything in it. Confirm `down_revision` points at the true current head and nothing looks hand-altered from what autogenerate would actually produce.
3. **Confirm Rewriter coverage.** It only reaches `CreateTableOp`/`CreateIndexOp`/`DropTableOp`/`DropIndexOp`. Everything else in the diff — `add_column`/`drop_column`, `AlterColumnOp`, enum value edits, any hand-written `op.execute()` — needs its own guard in **both** `upgrade()` and `downgrade()`, mirroring `2c77dd65027b`'s pattern exactly:
   ```python
   bind = op.get_bind()
   inspector = sa.inspect(bind)
   columns = {c["name"] for c in inspector.get_columns("<table>")}
   if "<column>" not in columns:
       op.add_column("<table>", sa.Column(...))
   ```
4. **PostgreSQL hazards pass** — check the diff against each (no in-repo exemplar covers (a)/(b); build them fresh from `references/postgres-hazards.md`):
   - (a) A `CREATE INDEX CONCURRENTLY` goes in its own migration, inside `with op.get_context().autocommit_block():`, with `if_not_exists=True`.
   - (b) A new enum value (`ALTER TYPE ... ADD VALUE`) is added in a migration separate from the one that first uses it — PG15 cannot use a value added earlier in the same transaction.
   - (c) Any data backfill is idempotent (`WHERE col IS NULL`, `ON CONFLICT DO NOTHING`), batched, and kept separate from DDL, guarded the same way as step 3.
   - (d) Any destructive change (drop column/table, tighten a `NOT NULL`) is one phase of an expand→migrate→contract sequence across releases, not a same-release drop of something the previous release's code still reads.
5. **`downgrade()` must be real.** Reverse every `upgrade()` operation with the same guard style, never `pass`. If an upgrade step is genuinely irreversible (a lossy backfill), `downgrade()` still restores the schema shape and documents the data-loss caveat in a comment — it does not silently no-op.
6. **Prove it — actually run the commands, don't assert the result:**
   ```
   alembic upgrade head
   alembic downgrade -1
   alembic upgrade head
   ```
   Capture and quote the real output in the report. A guard prevents a hard failure; only this cycle proves correctness.
7. **History discipline.** Never edit, delete, or re-parent an existing revision file. A conflicting `down_revision` across branches is resolved with `alembic merge`, never a hand edit.
8. **Report** the revision id, what it guards and why, and the verbatim upgrade→downgrade→upgrade output.

## Constraints

- Never edit `migrations/env.py` (`AGENTS.md` §7.9 — config files are read-only to agents).
- Never hand-set `revision`/`down_revision` outside what `alembic revision`/`alembic merge` actually generated.
- No raw `CREATE`/`ALTER`/`DROP` without a guard; no `create_all()` anywhere.
- Never claim the upgrade/downgrade/upgrade cycle passed without having actually run it.

## Verification Checklist

- [ ] Revision message is a real, specific snake_case description.
- [ ] The generated file was read in full before being trusted.
- [ ] Every autogenerated create/drop table/index directive carries `if_not_exists`/`if_exists` — confirmed present, not assumed.
- [ ] Every `add_column`/`drop_column`, `AlterColumnOp`, enum edit, and hand-written `op.execute()` has its own `sa.inspect(op.get_bind())` guard in both `upgrade()` and `downgrade()`.
- [ ] Any `CONCURRENTLY` index is in its own migration inside `autocommit_block()` with `if_not_exists=True`.
- [ ] Any new enum value is added in a transaction separate from its first use.
- [ ] Any backfill is idempotent, batched, and separate from DDL.
- [ ] Any destructive change is staged expand→migrate→contract.
- [ ] `downgrade()` performs real inverse operations — never `pass`.
- [ ] `upgrade → downgrade → upgrade` was actually executed and its real output is quoted in the report.
- [ ] No existing revision file was edited, deleted, or re-parented; `migrations/env.py` untouched.

## Outputs

- One new `migrations/versions/<hash>_<description>.py`.
- The captured proof output, in the chat report.

## Completion Criteria

Complete only when the checklist above is fully satisfied and the real `upgrade → downgrade → upgrade` output has been captured and quoted — never asserted without having run it.
